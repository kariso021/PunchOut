# PunchOut — 스토리와 학습 병행 체크리스트

작성 기준: 2026-11-01. 이 문서는 구현 계획이자 학습 기록이다. 체크는 학습자가 설명과 실험으로 확인한 뒤 표시한다. 코드가 이미 존재하거나 AI가 설명했다는 이유만으로 학습 완료 처리하지 않는다.

## 운영 방식

- 스토리 장면 하나를 정하고, 플레이어가 할 행동과 성공 조건을 먼저 적는다.
- 그 기능에서 배우려는 개념을 1~2개 고른다. 전체 개념은 아래 목록으로 관리하되 한 기능에 모두 넣지 않는다.
- 구현 전에 학습자가 소유권·수명·실행 흐름을 판단한다. AI는 근거와 반례를 검토한다.
- 작은 기능을 구현하고 예상과 실제 결과를 비교한다.
- 구현 완료와 학습 완료는 따로 기록한다. 판단이 바뀌었다면 원래 판단을 지우지 않고 수정 근거를 남긴다.
- 모든 학습은 프로젝트의 장면 또는 문제와 연결한다. 실제 게임에 필요 없는 알고리즘, 스레드, 그래픽스 API는 프로젝트 내 독립 실습으로 검증하고 런타임에 억지로 추가하지 않는다.
- DX12를 먼저 학습하고 Vulkan/OpenGL은 같은 개념의 차이를 비교한다. 실제 API 구현 전에는 사용 버전의 공식 문서를 확인한다.

- [ ] 메모리 소유권, 참조 관계, GAS 역할, 네트워크 권한을 구분했다.
- [ ] 누가 상태를 읽고 변경하는지 정했다.
- [ ] 실행 순서와 실행 위치(스레드, 서버/클라이언트)를 정했다.
- [ ] 연결·해제·취소·파괴 시점을 정했다.
- [ ] 대상 소멸, 중복 요청, 늦게 도착한 결과를 어떻게 처리할지 판단했다.
- [ ] 더 단순한 구현과 비교하고 이 방식을 선택한 이유를 적었다.

판단과 근거:

**구현 후 확인**

- [ ] 정상 경로와 이 기능에 중요한 실패/취소 경로를 실행했다.
- [ ] 관찰 결과를 구현 전 예상과 비교했다.
- [ ] 설명할 수 없는 코드와 아직 확인하지 못한 가정을 표시했다.
- [ ] 비용이 문제라면 같은 조건에서 변경 전후를 측정했다.
- [ ] 코드/에셋 경로, 커밋, 캡처 또는 로그를 기록했다.
- [ ] 구현을 보지 않고 소유권과 실행 흐름을 설명했다.

## 스토리 진행과 연결할 학습 단계

아래 장면은 기능을 연결하기 위한 임시 예시다. 확정된 줄거리·캐릭터·사건은 사용자가 작성하고 이 자리에 연결한다.

### 0. 플레이어가 장면에 들어온다 — 현재 기반 이해

스토리 장면: __________

- [ ] PlayerState → ASC 소유, ASC ↔ Pawn 연결을 그림으로 설명한다.
- [ ] 객체 수명과 포인터 변수의 수명이 다름을 설명한다.
- [ ] 강한 참조와 약한 참조의 차이를 현재 코드로 설명한다.
- [ ] UObject 수명 관리와 일반 C++ RAII를 구분한다.
- [ ] GAS OwnerActor, AvatarActor, Actor의 네트워크 Owner를 구분한다.
- [ ] Possess/UnPossess, Pawn 교체, EndPlay 순서를 로그로 확인한다.
- [ ] 이전 Pawn 종료가 새 Avatar 연결을 지우지 않는 이유를 테스트로 설명한다.

현재 구현 근거: PunchOutCore의 PlayerState/Pawn, PunchOut.Core.AvatarOwnership 테스트. 구현은 존재하지만 학습 체크는 아직 하지 않는다.

### 1. 이동하고 대상을 바라본다 — 좌표와 데이터

스토리 장면: __________

- [ ] 위치·방향·속도·델타 시간을 구분한다.
- [ ] 로컬/월드/뷰/클립 공간과 변환 흐름을 설명한다.
- [ ] 내적으로 정면 판정, 외적으로 수직 방향을 계산하고 화면에 표시한다.
- [ ] 행렬 곱 순서를 바꾸고 결과를 예측·검증한다.
- [ ] 값·참조 전달, const, 복사·이동의 의미를 관련 코드로 설명한다.
- [ ] 카메라와 이동의 조정값을 어디에 저장할지 판단한다.

증거: 디버그 표시와 예상 좌표, 관련 코드/에셋.

### 2. 첫 펀치를 실행한다 — GAS와 상태 전이

스토리 장면: __________

- [ ] 입력 → Ability 활성화 → 타격 판정 → Effect → Attribute 변화 흐름을 설명한다.
- [ ] Ability, Effect, AttributeSet, Tag의 책임을 구분한다.
- [ ] 공격 중 입력, 취소, 피격, 사망의 전이 조건을 정한다.
- [ ] 공격 설정과 실행 중 타깃/히트 결과를 분리한다.
- [ ] 콜백과 타이머의 소유자·취소 시점·캡처 수명을 확인한다.
- [ ] 피해를 결정하는 서버와 표현하는 클라이언트의 역할을 구분한다.
- [ ] 정상 타격, 빗나감, 중복 타격, 중간 취소를 검증한다.

증거: 첫 공격 기능과 실행 순서 로그. 실제 Ability/AttributeSet은 기준일 현재 미구현.

### 3. 적이 반응한다 — 알고리즘과 메모리

스토리 장면: __________

- [ ] 타깃 선택에 필요한 자료구조와 시간 복잡도를 설명한다.
- [ ] 적별 가변 상태와 공유 설정을 구분한다.
- [ ] 연속 메모리·포인터 추적·캐시 지역성을 비교 실험한다.
- [ ] 컨테이너 변경 시 참조/반복자가 무효화되는 조건을 확인한다.
- [ ] 계산할 때마다 필요한 할당과 재사용 가능한 데이터를 구분한다.
- [ ] 여러 적, 타깃 소멸, 공격 실패에서 상태가 섞이지 않는지 검증한다.

증거: 입력 크기별 시간 기록과 복수 AI 동작 결과.

### 4. 여러 일이 겹친다 — 비동기와 병렬 처리

스토리 장면: __________

- [ ] 비동기와 병렬 처리를 각각 실행 흐름으로 설명한다.
- [ ] 작업을 보내는 스레드, 실행하는 스레드, 결과를 적용하는 스레드를 구분한다.
- [ ] 게임 상태를 값으로 복사한 뒤 독립 계산하는 실험을 만든다.
- [ ] 데이터 경쟁, 임계 구역, 동기화, 데드락을 작은 사례로 설명한다.
- [ ] 약한 포인터가 스레드 안전성을 보장하지 않음을 설명한다.
- [ ] 작업 완료 전에 대상이 사라지거나 새 요청이 발생한 경우를 검증한다.
- [ ] 순차/병렬 실행을 작은 입력과 큰 입력에서 비교한다.
- [ ] 병렬화 비용을 포함해 실제 게임에 적용할지 판단한다. 적용하지 않는 결론도 유효하다.

증거: 실험 코드와 측정값, 런타임 채택 여부 및 근거.

### 5. 장면을 보여준다 — 엔진 렌더링과 GPU

스토리 장면: __________

- [ ] CPU 게임 처리 → 렌더링 명령 준비/제출 → GPU 실행을 설명한다.
- [ ] 한 프레임에서 캐릭터의 드로 호출과 입력/출력 자원을 찾는다.
- [ ] 정점 처리·래스터화·픽셀 처리·깊이 테스트·블렌딩을 구분한다.
- [ ] 원근 투영, 법선, 내적 조명을 화면 결과와 연결한다.
- [ ] 머티리얼 또는 후처리 효과 하나를 구현한다.
- [ ] 효과가 읽고 쓰는 데이터와 렌더링 단계를 확인한다.
- [ ] 관련 엔진 소스 진입점과 호출 흐름을 따라간다.

증거: 프레임 캡처, 효과 화면, 관련 엔진 소스 위치.

### 6. 같은 화면을 아래 계층에서 만든다 — DX12 실습

연결할 게임 화면/효과: __________

실습은 예를 들어 Labs/Graphics 아래 별도 빌드 대상으로 둔다. Unreal 모듈에 독립 DX12 렌더러를 섞지 않는다. 현재 실습 프로젝트는 생성하지 않았다.

- [ ] Device, Swap Chain, Render Target으로 화면을 지운다.
- [ ] Command List/Queue로 삼각형을 그린다.
- [ ] 버퍼·행렬·HLSL로 회전하는 큐브를 그린다.
- [ ] PSO, Root Signature, Descriptor의 역할을 설명한다.
- [ ] 텍스처 업로드 및 자원 상태 전환을 구현한다.
- [ ] CPU 메모리 수명과 GPU 사용 완료 시점의 차이를 설명한다.
- [ ] Fence와 프레임별 자원으로 사용 중인 데이터를 덮어쓰지 않게 한다.
- [ ] 디버그 계층의 오류를 확인하고 해결 과정을 기록한다.
- [ ] Vulkan/OpenGL에서 같은 자원·제출·동기화 개념이 어떻게 표현되는지 공식 문서로 비교한다.

증거: 독립 실행 데모와 CPU/GPU 타임라인 설명. API 세 개의 구현을 모두 완료해야 하는 단계는 아니다.

### 7. 장면이 느려진다 — 성능 분석

스토리 장면 및 재현 조건: __________

- [ ] FPS 대신 ms 기준으로 CPU/GPU 프레임 시간을 기록한다.
- [ ] CPU/GPU 실행이 겹치는 이유와 대기 구간을 설명한다.
- [ ] 동일한 장면·카메라·해상도·빌드·하드웨어로 비교한다.
- [ ] 해상도, 객체 수, 그림자, 반투명을 하나씩 바꿔 측정한다.
- [ ] CPU 계산/메모리/대기, GPU 연산/대역폭/오버드로 중 가설을 세운다.
- [ ] SIMD와 GPU 웨이브 실행·분기 발산을 사례로 설명한다.
- [ ] 변경 전후 반복 측정과 프레임 변동을 기록한다.
- [ ] 화질·메모리·코드 복잡도와의 교환 비용을 설명한다.
- [ ] 개선 실패 또는 효과 없음도 근거와 함께 기록한다.

증거: 문제 → 가설 → 변경 → 측정 → 결론의 개선 사례 하나.

### 8. 장면과 규칙을 조합한다 — 모듈·초기화·네트워크

스토리 장면: __________

- [ ] Core/Combat/OfficeGame/FrontEnd에 넣을 책임을 판단한다.
- [ ] 헤더 의존성, 전방 선언, 번역 단위, 컴파일과 링크를 설명한다.
- [ ] 모듈 의존 방향과 순환 의존을 확인한다.
- [ ] Experience 로딩과 기능 활성화/해제 순서를 설명한다.
- [ ] Ability 부여·회수와 입력 연결·해제가 대칭인지 검증한다.
- [ ] 로컬 상태, 복제 상태, 서버 권한, 예측 상태를 구분한다.
- [ ] 두 플레이어, Pawn 교체, 연결 해제에서 기능을 검증한다.
- [ ] 패키징 빌드에서 같은 스토리 구간을 실행한다.

증거: 의존 관계와 초기화 순서, 네트워크/패키징 검증 기록.

## 첫 학습 세션

- [ ] 사용자가 첫 스토리 장면과 플레이어의 목표를 적는다.
- [ ] 현재 PlayerState/ASC/Pawn의 소유·참조 관계를 코드 보기 전에 예상한다.
- [ ] 실제 코드를 읽고 예상과 비교한다.
- [ ] Pawn 교체 테스트가 무엇을 보장하고 무엇을 보장하지 않는지 설명한다.
- [ ] 다음 구현 기능 하나와 학습 개념 두 개 이하를 고른다.

학습자가 답하기 전에 AI가 판단란을 대신 완성하지 않는다. AI는 코드 탐색·구현 초안·검증 도구를 돕되, 학습 완료 체크는 학습자의 설명과 증거를 바탕으로 함께 결정한다.
